# Wave 40 — One Real mode, operator Execution OFF/ON switch, existing risk limits

## Superseding operator decision (2026-10-10)

**This is the authoritative Wave 40 contract.** It replaces earlier instructions for a separate canary launcher, one-opportunity/one-trade run, hard-coded £3/£5 test limits, £5 aggregate session budget, stop-after-one-trade, mandatory per-trade confirmation, or timed expiry of otherwise healthy continuous execution. Those were extra proposals, **NOT part of the operator's intended Sports Hedge design**. Do not implement them.

The operator specifically wants to test **normal, continuous, multi-opportunity Sports Hedge REAL execution using the existing immaterial operator-configured placement limits**, rather than a constrained test mode. There should be **ONE Real mode, ONE normal Real-mode launcher, and an Execution OFF/ON switch at top right**. A fresh backend launch ALWAYS starts OFF. When the operator confirms ON, approved HOT, BACKGROUND and STREAM opportunities may continuously progress through the **same authoritative Price-2 and existing execution system**, until switched OFF or blocked by actual risk/market/venue controls. **No artificial aggregate session budget and no automatic stop after the first trade.**

Screenshot supplied by operator of an existing **PAPER MODE** controls section shows **MAX EVENT £7, MAX OPPORTUNITY £7 and MAX ONE-TIME £5**. These are already system-defined operator placement limits, not a new session cap. **At execution time, use the currently persisted effective operator settings** rather than hard-code even the screenshot's numbers: `effective_operator_scanner_settings(settings)` supplies `max_event_gbp`, `max_opportunity_gbp`, `max_one_time_gbp`; `arbitrage/allocation/policy.py::policy_from_settings` also includes existing treasury, venue, open-capital, same-fixture and portfolio exposure limits. Never silently override a configured £7/£7/£5 to £5/£5/£3 or expand any limit to get an order through.

## Safety boundary — do not confuse with artificial trading restrictions

- **The normal Windows Real launcher remains the only Real launcher.** `scripts/windows/Start-SportsHedge-Real.ps1` starts the scanner with execution OFF; `SPORTS_HEDGE_EXECUTION_ENABLED=false` and `PAPER_AUTOFILL_ENABLED=false` remain safe process startup defaults. Do not require changing .env, opening a separate app, or restarting to toggle execution.
- **A top-right Real header switch controls server-authoritative live execution arming**. OFF keeps scanner, market data, STREAM, HOT, BACKGROUND, Price-2, diagnostics, monitoring/reconciliation running and cannot submit new live orders. Turning ON requires an explicit first-run confirmation that real money may be wagered, supported venue account/current-IP territory checks and authenticated local operator intent. Do not ask the operator to approve every subsequent qualifying trade. ON remains ON during normal scanning, not automatically halted after one opportunity; a backend restart resets arming OFF. Browser refresh reads server status rather than optimistically assuming ON.
- **Disarming** immediately closes the new-order authorization gate, including independently triggered HOT/BACKGROUND/STREAM captures, without falsely reporting cancellation of orders already submitted or stopping monitoring/reconciliation of open and unknown fills. An order already sent before OFF still needs reconciliation, even after restart. Protect runtime arming endpoint against untrusted nonlocal requests, cross-origin/CSRF attacks and races; never expose API credentials/secrets. Status reads have no venue side effects. A disabled frontend toggle is NOT sufficient to block backend order submission.
- Runtime arming must integrate the **existing execution guards** in `execution/package.py`, `execution/dispatch.py`, `execution/composition.py`, `application/paper_operations.py`, and the venue transports. The existing `execution_armed(settings)` depends on immutable startup configuration; implement a fail-closed runtime switch *consistently at the authoritative dispatch boundary* without accidentally treating `SPORTS_HEDGE_EXECUTION_ENABLED=false` as permission or keeping dormant bypass routes. Do not simply remove dispatch checks or turn the paper-autofill flag true for all modes. Use one coherent runtime activation gate for normal continuous capture.
- **All existing operator-configurable limits and existing risk/treasury controls remain mandatory.** This includes the persisted per-event, per-opportunity and per-one-time caps, portfolio and venue balances, existing active exposure, reservation/inflight management, exact native order stake/rounding/minimum sizes, risk and settlement checks, matching registration, stable native IDs, economically known fees/FX and accepted 0.20% net minimum (or the actual saved operator threshold), Price-2 default 500ms skew / 2000ms freshness (or actual configured thresholds), and the generalized payoff guarantee. Enforce caps against aggregate *currently committed/open/pending* exposure with atomic shared state, not only frontend presentation. No new arbitrary £5 lifetime/session limit.
- **Venue/platform availability and permission remain necessary.** Before ON, conduct read-only Matchbook and Polymarket account/venue eligibility checks (current outbound IP, balance, allowance, spendable cash/currency, open/unknown orders, permissions). If a venue rejects, is unreachable, or the operator cannot lawfully trade at the endpoint's real location, fail closed rather than bypass geo/terms or spoof IP. Persistent trade-on eligibility should be checked appropriately, not assumed from a launch-time flag alone. No hardcoded fees/FX, no assumptions to fill missing data.
- **Native exchange minimums** may make a very small opportunity infeasible; reject that individual opportunity and report the actual reason. Do NOT automatically inflate max one-time/event/opportunity or create paper-only fictitious fills.
- Preserve existing **partial/unknown/remainder/idempotency protections**, the native frozen Price-2 execution package, cancellation of known resting Matchbook remainders, no blind retry of ambiguous submissions, no new speculative hedge after a nonreconciled opening, and only genuine reconciled fully hedged top-ups. An unresolved/unhedged order can lock the appropriate at-risk funds and trigger existing protective behaviour, but must not invent a global one-trade-per-session restriction.
- Clear audit through `candidate -> Price-2 attempted -> rejected/accepted -> native orders attempted -> each exchange ACK/fill -> partial/unmatched/unknown -> reconciled -> active trade / realised P&L`. A `Price-2 accepted` quote is *not* a trade entered. Keep audit logs meaningful for troubleshooting real outcomes and never claim speculative gross or net edges were realised.
- A successful single trade does not prove all venue/fill failure paths, and small position size does not guarantee both legs execute. However, **the goal of this wave is testing the intended system at the existing immaterial configured limits**, not shipping a different single-trade workflow.

## Existing Paper/Real configuration parity — do not rebuild

The operator has reconfirmed: **Real mode already has these exact same three placement controls.** This is not a request to implement, duplicate, migrate or redesign the Max Event / Max Opportunity / Max One-Time controls. Their existing values and save paths must be preserved in both modes, and switching Execution ON/OFF must not alter any of them.

**Verified existing shared code:**
- `frontend/components/run-paper-scan.tsx` already displays/loads/saves these three fields via the backend's operator settings API. There is currently a misleading literal `PAPER MODE · NO EXECUTION` in its section heading at ~line 774 (and another prose label at ~line 1240). Make mode wording derive from actual runtime state, showing Real mode accurately; leave the form/controls themselves alone.
- `backend/src/sports_hedge/api/paper.py` implements `GET /operator-scanner-settings` and `PUT /operator-scanner-settings` through the existing coordinator/store; the historical `paper` module name is not a reason to duplicate the settings in a `real` module.
- `backend/src/sports_hedge/persistence/operator_scanner_settings.py::effective_operator_scanner_settings` resolves the shared source.
- `backend/src/sports_hedge/arbitrage/allocation/policy.py::policy_from_settings` already reads shared `max_event_gbp/max_opportunity_gbp/max_one_time_gbp`, with existing venue/treasury/portfolio constraints; `application/paper_scan.py` uses that policy.
- `application/paper_operations.py` and `application/price_engine.py` also read effective operator settings, without independent Real/Paper cap sets.

**Only missing feature:** the backend-authoritative runtime execution arming toggle and appropriate dynamic header/status labels. Minimise changes to scanner controls and pricing/allocation; avoid introducing mode-based branch logic for fee/capital limits. If Real mode renders a Paper badge, fix the badge, not the allocation authority. A Real-mode dashboard has the same controls and live market data whether Execution is ON or OFF.
